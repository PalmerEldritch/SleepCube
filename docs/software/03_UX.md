# SleepCube User Experience Specification

**Revision:** R00

## 1. Interaction model

The R00 UX retains the current touch-first ambient concept already implemented on the Waveshare controller.

The UI has two primary modes:

- **Rest view** — default ambient visual state used during normal operation.
- **Adjustment view** — temporary volume/brightness controls entered by long press.

## 2. Rest view requirements

| ID | Requirement |
| --- | --- |
| UX-UI-001 | The rest view shall be the default steady-state UI after startup. |
| UX-UI-002 | A short tap in the rest view shall request audio playback toggle. |
| UX-UI-003 | A long press of approximately 1 s shall enter the adjustment view. |
| UX-UI-004 | Significant pointer movement during a rest-view gesture shall cancel long-press recognition and shall not be interpreted as a short tap when the pointer is released. |
| UX-UI-005 | The rest view shall remain visually useful as part of the ambient presentation and shall not behave as a conventional menu screen. |
| UX-UI-006 | Audio state changes may produce a short visual pulse/response in the display and lighting engine. |

## 3. Adjustment view requirements

| ID | Requirement |
| --- | --- |
| UX-UI-010 | The adjustment view shall provide direct volume and brightness adjustment without nested menus. |
| UX-UI-011 | The two controls shall be spatially distinct and usable by direct touch/drag interaction. |
| UX-UI-012 | The adjustment view shall initialize controls from the current software state. |
| UX-UI-013 | The adjustment view shall return automatically to the rest view after approximately 3 s of inactivity. |
| UX-UI-014 | Entering or leaving the adjustment view shall use a short visual transition rather than an abrupt overlay change. |
| UX-UI-015 | Brightness adjustment shall remain available when audio is unavailable. |
| UX-UI-016 | While the Audio Controller is unavailable, volume input shall be ignored and the volume control shall retain the last confirmed value rather than indicate an unconfirmed change. |

## 4. Audio-state presentation

| ID | Requirement |
| --- | --- |
| UX-AUD-001 | The UI shall distinguish a confirmed playing state from a confirmed stopped state. |
| UX-AUD-002 | The UI shall not present audio as confirmed playing solely because a play command was transmitted. |
| UX-AUD-003 | During startup or loss of synchronization, the UI may use a neutral/degraded audio state until authoritative state is received. |
| UX-AUD-004 | Audio timeout shall return the UI to the stopped state without altering the user's selected lighting brightness. |

For R00, loss of audio synchronization uses the existing neutral rest
presentation: the confirmed-playing boost is removed, no start/stop pulse is
generated solely by link loss, and normal ambient lighting and brightness
control continue. Recovery may present a state pulse only after authoritative
status has been reacquired.

## 5. Low-light behaviour

| ID | Requirement |
| --- | --- |
| UX-LGT-001 | The display/backlight shall use smooth low-frequency ambient modulation suitable for a dark room. |
| UX-LGT-002 | User brightness selection shall influence both the external light presentation and display brightness in a coordinated manner. |
| UX-LGT-003 | Normal UI operation shall avoid persistent bright status indicators. |
| UX-LGT-004 | Transient visual indications shall decay automatically and shall not leave the display in a high-brightness status state. |

The display retains the complete user-selectable brightness range. The external
LED output may apply a hardware-specific low-level floor when enabled so that
extreme settings and transient dips preserve the intended warm-white color
rather than exposing unstable low-count RGB quantization. This floor does not
change the stored user setting or prevent a commanded lighting shutdown.

## 6. Startup and recovery behaviour

| ID | Requirement |
| --- | --- |
| UX-STA-001 | Startup shall show the ambient visual presentation without automatically starting audio. |
| UX-STA-002 | Temporary Audio Controller unavailability shall not prevent entry to the normal rest view or brightness adjustment. |
| UX-STA-003 | Recovery of the Audio Controller shall occur without requiring a user restart of the Control Controller. |

## 7. Current implementation reuse

The current Waveshare implementation already provides the intended baseline interaction pattern: rest-view tap for playback toggle, ~1 s long press for slider mode, split volume/brightness adjustment zones, ~3 s inactivity timeout, animated overlay transition and ambient backlight modulation. These behaviours should be preserved unless a later UX review explicitly changes them.
